# loopForge：spawn 运行时逻辑规则

> **性质**：`loopForge` 模块**内部**对 **spawn 父子 Agent** 的**行为契约**（**逻辑规则**），供实现、评审与 `doc/log` / `doc/plan` 引用；**不是** Cursor 或编辑器侧规则。  
> **设计承接**：`doc/design/multi-agent-engine.md` §3.8。

---

## 1. 父子上下文隔离 + 可传递的精简短期记忆

- **默认隔离**：子 Agent 的**可写上下文**与父级**互相独立**；子级 **不** 默认获得父对话的**全量**历史。  
- **受控下传**：父级 Agent **允许**向子级注入经**产品策略精简**后的**短期记忆**（例如**摘要、近期若干轮、或结构化 scratch**），**不得** 等同于父侧**全量** transcript 的自动复制。  
- **落点**（实现时）：`SpawnSpec` 中已有字段（如 `system_addendum`、`task`）与**可选的「父侧记忆下传块」**（**英文** 字段名与结构在实装中定义，例如与 `doc/log/progress-v0.8.0` 的「待决」同步）。

---

## 2. 父级 Run 终止时，子 Agent 须退出

- 当**父级 Agent 对应的根 Run 结束**（**完成**、**取消**、**错误** 等**终态**）时，**所有**由该父系 spawn 出、仍存活或**处于等待唤醒** 的子 Agent，**必须**被**强制**回收并退出。  
- **原因**：子级的生命周期**从属于** 父级 Run 的资源与观测边界；**避免** 父已结束而子**泄漏** 协程、会话或 **MCP** 连接。  
- 与子规则 **§3** 的衔接：即父在 spawn 时选择「子**单次**结束后**是否**保持可再唤醒」；**一旦父级 Run 全局结束**，**不再**保留任一等候中的子级。

---

## 3. 子 Agent 单次执行结束后的存留：由父级在拉起时决定

- 子 Agent **一次子 Run 执行到自然结束**（子任务完成、**max steps**、**子层超时** 等）后，**两种** 语义**至少** 二选一，且由**父级在发起 spawn 时**显式指定或等价**默认**（**须在实现与** `SpawnSpec` / 配置 **中可表达**）：
  - **完成后自动结束（ephemeral for this sub session）**：子**交付** `SpawnResult` / **tool result** 后，子 Agent **即** 结束该子**生命周期**；若父**再次**需要子能力，**须** 再次 **spawn**（**新**子 `Run` / 新**实例**语义由实现定稿，但**不得** 与 §4 的**非阻塞** 冲突）。  
  - **完成后进入可唤醒等待态**：子**不** 立即释放执行体，在**有界资源** 下**阻塞在** 等待**父** 的下一次**唤醒**（**再次**下发子任务/指令，由产品约定**一**种通道，例如**同一** 工具**通道** 或**引擎** 内部消息）。**是否在执行结束后自动退出**由 **该次 spawn 的选项** 决定，**不** 由子侧自行猜。  
- 与 **§2** 的优先级：**父 Run 全局终态** **高于** 子**等待唤醒**；**父一结束，子** **一律** 退出（见 §2）。

---

## 4. 子 Agent 在独立协程中执行，不得阻塞父 Agent

- 子 **Run** 的**推进**（子 loop、子 tool 调用等）**必须** 在**独立** `goroutine`（或等价**异步**执行单元）中**进行**，**使** 父级 Agent 的**主**执行路径（**父** 的**推理/工具/事件** 循环）**不** 因**等待** 子**跑完** 而**长期同步阻塞**（**尤其** 禁止在**父** 的**同一线程/热路径** 上**直接** `Run` 子**完整** 子 `RunLoop` 直至结束）。  
- **允许的** 同步点：仅**可接受**的、**有界** 的**信令**（例如**极短** 的**起停** 或**结果句柄** 写入；**不** 等同于「父**等** 子**整个** 子树**步数**跑完再返回」）。**父** 在**子未** 完成时**必须** 能**继续** 收事件/调度/取消（与 **ctx** 语义相洽）。  
- **与** 旧版「MVP 可同步子 Run」**的** 关系：以**本文** **§4** 为**准**；若 `doc/plan` / `progress` 中曾写**同步** `Spawn` 内**跑完** 子**整** loop，**实现** 上应**改为** **异步** + **结果** 通过**通道/回调/工具结果** **回填**，并**回写** 计划文档。

---

## 5. 嵌套 spawn 的父级显式授权（默认禁止）

- **总开关**：子 Agent **默认不得** 再次 spawn 新的子 Agent；只有在父级**发起本次 spawn 时**于 `SpawnSpec` 中**显式授权**（如 `AllowChildSpawn = true`），子级才被允许在自身 loop 中调用 `spawn_subagent`。  
- **作用域**：授权**只对当前被拉起的子级**生效；该子级若想让**自己的下一级孙子** 继续 spawn，**仍** 必须在它发起的 `SpawnSpec` 中**再次** 显式授权 —— **逐级显式、不传递、不继承**。  
- **与 `LoopPolicy.MaxDepth` 的关系**：两者**叠加生效**，**取最严**——即使 `MaxDepth > 1` 允许嵌套，若父级未授权，子级 spawn 仍被引擎拒绝并返回 `SpawnRejected`（`Code = "child_spawn_forbidden"` 或等价语义）；反之，若父级授权但深度已达 `MaxDepth`，仍按 `MaxDepth` 拒绝。  
- **工具暴露**：实现上等价于在子级的 `ToolRegistry` 中**条件性注册** `spawn_subagent`：未授权时**根本不挂载** 该工具，避免模型「看得见但调不通」造成幻觉。  
- **观测**：拒绝须可观测（`slog` + `SpawnRejected` 事件）；授权链应在 trace 中可回放（`parent_run_id` 链 + 每级 `allow_child_spawn` 属性）。

---

## 6. 子 Agent 调用大模型时强制非流式

- **子 Run 内** 的 **LLM 调用**（`Generate` / 等价入口）在 **spawn 子 Agent** 路径上 **须** 使用**非流式**（**non-streaming** / 单次完整响应体），**不** 使用**边生成边出 token** 的**流式** 传输（若底层 SDK 分 **stream** 与 **non-stream** 两种 API，**子** 固定走 **non-stream** 分支或等价的「整包返回」实现）。  
- **目的**：降低**长连** 与**分块** 链路上的**网络开销**与**对基础设施** 的压力；子任务多为**短子 Run**，**全量** 回包通常可接受。若个别场景**必须** 子侧流式，**须** 作为**显式** **例外**（产品开关或 `SpawnSpec` 中**可选** 的 `allow_stream` 等**英文** 字段，**默认** `false`）并**在评审** 中记录，**默认** 仍为**非流式**。  
- **与父** 的区分：本条**只约束** **spawn 子** Agent 的**模型** 调用；**根 / 非 spawn** 路径的**流式/非流式** 由既有 **Runner/Agent 配置** 决定，**不** 被本条**覆盖**（除非**全局** 策略**另有** 规定）。  
- **落点**（实现时）：在**构造** 子 **`ChatModel` 包装** 或**子** `**Run` 的 **model** 旁路 上 强制 **`stream=false`**（或**等价**），并**在** 验收中**可观测**（日志或 trace 属性，如 `llm_mode=non_stream`）。

---

## 7. 子 Agent 工具集：与父同源 + 父级双名单过滤 + ReAct 结果聚合

- **工具来源同源**：子 Agent 的 `ToolRegistry` **默认** 与父 Agent **同源**——同一份 MCP 绑定与同一份内置工具集；**不** 为子级创建独立的工具仓库（避免「父能调子不能调」造成的能力漂移）。  
- **父级双名单过滤**：父级在 `SpawnSpec` 中通过**白名单 + 黑名单**对子级**实际可见**的工具进行**收敛**：  
  - `tool_white_list`：若**非空**，子级**仅** 允许调用列表内工具；为空表示「不主动收敛」。  
  - `tool_block_list`：始终生效；命中即**不** 暴露给子级（即便在白名单中也不暴露）。  
  - 两表**同时**作用时，**先** 应用白名单**再** 应用黑名单（**取交集后再扣黑名单**）；与 §5 嵌套 spawn 授权**正交**——`spawn_subagent` 是否对子级可见**仍** 由 `AllowChildSpawn` 决定，**不**走双名单。  
- **ReAct 中间步骤对父侧不可见**：子 Agent 在自身 ReAct（推理 / `function_call` / `tool_result` 多轮）过程中产生的**中间** function-call、`tool_result`、思考文本，**不** 流式回填到父级；父级**只**收到子级**最终结果**（一次 `SpawnResult`）。  
  - **目的**：父级模型不被子级中间步骤污染上下文、不重复扣 token，也避免上层调用方为「子的中间过程」付费或误展示。  
- **最终结果须附带 function_call 摘要以便父侧外发**：子级在产出 `SpawnResult` 时，**须** 同时附带本次 ReAct 期间产生的 **function_call 调用清单**（结构化、按发生顺序），供**父 Agent** 在向**外部**（如外部事件流 / Tracing / 用户面）**转发** 工具调用报文时使用。  
  - **建议字段**（命名以代码评审为准）：`SpawnResult.ToolInvocations []ToolInvocation`，每项含 `Name` / `Arguments` / `ResultDigest` / `StartedAt` / `EndedAt` / `Error` / `MCPSource`；**不** 携带原始大体积 `tool_result` 全文，必要时只放摘要或外链。  
  - **观测**：子级仍在自身 trace 内记录完整 ReAct；父侧只在 `spawn_end` 事件 + `SpawnResult` 中拿到聚合后的 `ToolInvocations`，由父 Agent 决定是否向外发送、如何脱敏。  
- **与硬限制叠加**：双名单**不** 覆盖**深度 / 并发 / 预算** 等硬限制；任何工具调用仍受 `LoopPolicy` 与子树预算约束。
