# loopForge Plan 模式设计

> 本文档描述 loopForge **Plan 模式**的架构设计——Agent 驱动的结构化计划与执行机制。Plan 作为 Runner 层级的共享契约，通过工具（`plan_generate` / `plan_update`）与 Agent 交互，跨 transfer 自然传递。
>
> **前置阅读**：[02-runner-core.md](02-runner-core.md)——Runner 当前执行流程与 transfer 编排；[00-abstractions.md](00-abstractions.md)——整体分层架构。
>
> **关联 PRD**：`doc/PRD/prd-v0.10.0-plan.md`

---

## 1. 概念

### 1.1 Plan 是什么

Plan 是 Runner 层级的**结构化执行契约**。Agent 分析用户 Query，判断复杂度：

- **简单 Query**：不生成 Plan，走常规单 Agent 执行路径（如同 `RunModeSingleAgent`）
- **复杂 Query**：Agent 调用 `plan_generate` 工具输出结构化 Plan，Runner 拦截解析后注入所有后续 Agent 的 System Prompt

```
用户: "分析这份财报，计算几个关键指标，然后写成报告"
                  │
                  v
┌─── Agent ──────────────────────────────────┐
│  分析: "这是一个需要 3 步的复杂任务"           │
│  → plan_generate({                        │
│      title: "财报分析",                     │
│      steps: [                              │
│        {id:"s1", desc:"提取营收数据", ...},  │
│        {id:"s2", desc:"计算关键指标", ...},  │
│        {id:"s3", desc:"撰写报告", ...},     │
│      ]                                     │
│    })                                      │
└──────┬─────────────────────────────────────┘
       │ Runner 拦截
       v
┌─── PlanState ──────────────────────────────┐
│  Plan{Steps: [s1 pending, s2 pending, ...]} │
│  → 注入所有后续 Agent 的 System Prompt      │
└────────────────────────────────────────────┘
```

### 1.2 Plan 的职责边界

| 维度 | Plan | Agent |
|------|------|-------|
| 所有权 | **Runner**（PlanState） | 通过工具读写 |
| 生命周期 | 从 `plan_generate` 到 `query_end` | 每次 RunLoop（可能多 hop） |
| 可见范围 | 全部 Agent（跨 transfer） | 本 Agent 的 LoopState |
| 持久化 | 内存（PlanState） | 无状态 |

## 3. 数据模型

### 3.1 Plan

```go
// pkg/plan/plan.go

package plan

import "time"

// Plan is a structured execution plan generated by an agent and owned by the Runner.
type Plan struct {
	ID          string     `json:"id"`
	Title       string     `json:"title"`
	Description string     `json:"description,omitempty"`
	Steps       []PlanStep `json:"steps"`
	CreatedAt   time.Time  `json:"created_at"`
}

// PlanStep represents one step in the plan.
type PlanStep struct {
	ID          string         `json:"id"`
	Description string         `json:"description"`
	AssignedTo  string         `json:"assigned_to"`            // "self" | "spawn" | "transfer:AgentName" | "team:TeamName"(reserved)
	DependsOn   []string       `json:"depends_on,omitempty"`   // step IDs
	Status      PlanStepStatus `json:"status"`
	Result      string         `json:"result,omitempty"`
	StartedAt   *time.Time     `json:"started_at,omitempty"`
	CompletedAt *time.Time     `json:"completed_at,omitempty"`
}

// PlanStepStatus enumerates step states.
type PlanStepStatus string

const (
	PlanStepPending    PlanStepStatus = "pending"
	PlanStepInProgress PlanStepStatus = "in_progress"
	PlanStepCompleted  PlanStepStatus = "completed"
	PlanStepFailed     PlanStepStatus = "failed"
	PlanStepSkipped    PlanStepStatus = "skipped"
)
```

### 3.2 PlanState

```go
// pkg/plan/state.go

package plan

import "sync"

// PlanState is owned by the Runner and shared across agent hops.
// All exported methods are thread-safe.
type PlanState struct {
	mu   sync.RWMutex
	plan *Plan
}

// NewPlanState creates an empty PlanState.
func NewPlanState() *PlanState {
	return &PlanState{}
}

// SetPlan stores the plan. Returns an error if a plan already exists.
func (ps *PlanState) SetPlan(p *Plan) error {
	ps.mu.Lock()
	defer ps.mu.Unlock()
	if ps.plan != nil {
		return ErrPlanAlreadySet
	}
	ps.plan = p
	return nil
}

// Plan returns a read-only copy of the current plan.
func (ps *PlanState) Plan() *Plan {
	ps.mu.RLock()
	defer ps.mu.RUnlock()
	if ps.plan == nil {
		return nil
	}
	return ps.plan
}

// UpdateStepStatus updates the status and optionally the result of a step.
// On transition to/from in_progress, also updates StartedAt/CompletedAt.
// Returns ErrStepNotFound if stepID doesn't exist.
func (ps *PlanState) UpdateStepStatus(stepID string, status PlanStepStatus, result string) error {
	ps.mu.Lock()
	defer ps.mu.Unlock()
	if ps.plan == nil {
		return ErrNoPlan
	}
	for i := range ps.plan.Steps {
		if ps.plan.Steps[i].ID == stepID {
			now := time.Now()
			// Track transition times
			if status == PlanStepInProgress && ps.plan.Steps[i].Status != PlanStepInProgress {
				ps.plan.Steps[i].StartedAt = &now
			}
			if isTerminal(status) && ps.plan.Steps[i].Status != status {
				ps.plan.Steps[i].CompletedAt = &now
			}
			ps.plan.Steps[i].Status = status
			if result != "" {
				ps.plan.Steps[i].Result = result
			}
			return nil
		}
	}
	return ErrStepNotFound
}

func isTerminal(s PlanStepStatus) bool {
	return s == PlanStepCompleted || s == PlanStepFailed || s == PlanStepSkipped
}

// --- errors ---

var (
	ErrPlanAlreadySet = errors.New("plan already set, only one plan per run")
	ErrNoPlan         = errors.New("no plan set")
	ErrStepNotFound   = errors.New("step not found")
)
```

**Runner 拦截逻辑**（在 `runPlanLoop` 中，位于 Agent RunLoop 返回后）：

```go
// After agent returns from RunLoop, check for plan_generate intercept
func (r *Runner) handlePlanGenerateIntercept(ctx context.Context, ic *agent.InterceptedCall, ps *plan.PlanState) error {
	if ic == nil || ic.ToolCall.Name != "plan_generate" {
		return nil // not a plan_generate call
	}

	var params struct {
		Title       string              `json:"title"`
		Description string              `json:"description,omitempty"`
		Steps       []plan.PlanStep     `json:"steps"`
	}
	if err := json.Unmarshal([]byte(ic.ToolCall.Arguments), &params); err != nil {
		return fmt.Errorf("plan_generate: invalid arguments: %w", err)
	}
	if len(params.Steps) == 0 {
		return errors.New("plan_generate: at least one step required")
	}

	// Initialize step statuses
	for i := range params.Steps {
		if params.Steps[i].ID == "" {
			params.Steps[i].ID = fmt.Sprintf("step-%d", i+1)
		}
		if params.Steps[i].AssignedTo == "" {
			params.Steps[i].AssignedTo = "self"
		}
		params.Steps[i].Status = plan.PlanStepPending
	}

	p := &plan.Plan{
		ID:          uuid.New().String(),
		Title:       params.Title,
		Description: params.Description,
		Steps:       params.Steps,
		CreatedAt:   time.Now(),
	}

	if err := ps.SetPlan(p); err != nil {
		return err
	}

	// Emit event
	emit(0, &event.PlanGeneratedPayload{Plan: p})

	return nil
}
```

### 4.2 plan_update

Agent 用于更新 Plan 步骤状态的内置工具。

**Schema**：

```go
func planUpdateToolInfo() *model.ToolInfo {
	return &model.ToolInfo{
		Name:        "plan_update",
		Description: `Update the status and/or result of a plan step. Call this when you start working on a step (mark in_progress) or finish it (mark completed/failed).`,
		Parameters: map[string]interface{}{
			"type": "object",
			"properties": map[string]interface{}{
				"step_id": map[string]interface{}{
					"type":        "string",
					"description": "Step ID to update (e.g. \"step-1\")",
				},
				"status": map[string]interface{}{
					"type": "string",
					"enum": []string{"in_progress", "completed", "failed", "skipped"},
					"description": "New step status",
				},
				"result": map[string]interface{}{
					"type":        "string",
					"description": "Optional: description of what was accomplished or error details",
				},
			},
			"required": []string{"step_id", "status"},
		},
	}
}
```

**Handle 逻辑**（作为本地工具执行，非拦截）：

```go
func makePlanUpdateHandler(ps *plan.PlanState) model.ToolCallHandler {
	return func(ctx context.Context, argsJSON string) (string, error) {
		var params struct {
			StepID string          `json:"step_id"`
			Status plan.PlanStepStatus `json:"status"`
			Result string          `json:"result,omitempty"`
		}
		if err := json.Unmarshal([]byte(argsJSON), &params); err != nil {
			return "", fmt.Errorf("plan_update: invalid arguments: %w", err)
		}

		// Validate status
		switch params.Status {
		case plan.PlanStepInProgress, plan.PlanStepCompleted, plan.PlanStepFailed, plan.PlanStepSkipped:
		default:
			return "", fmt.Errorf("plan_update: invalid status %q", params.Status)
		}

		if err := ps.UpdateStepStatus(params.StepID, params.Status, params.Result); err != nil {
			return "", err
		}

		return fmt.Sprintf("Step %q updated to %s.", params.StepID, params.Status), nil
	}
}
```

> **注意**：`plan_update` 工具执行时，事件（EventPlanStepStart / EventPlanStepEnd）在 Runner 层发射。有两种策略：
> 1. **Handle 内发射**：简单直接，但 Handle 不一定能访问 event channel
> 2. **Handle 外包装**：Runner 在 `executeToolCalls` 的执行结果返回后扫描 PlanState 变更并发射事件
>
> v0.10.0 采用策略 2：PlanState 的变更由 Runner 的 runPlanLoop 在每步工具执行后检查，增量发射对应事件。

## 5. System Prompt 注入

Plan 生成后，在每个 Agent 的 System Prompt 末尾追加 `[Plan]` 块：

```
[Plan]
Title: 财报分析
Description: 提取数据、计算指标、生成报告

| Step | Description | Assigned To | Status |
|------|-------------|-------------|--------|
| step-1 | 提取营收数据 | self | completed |
| step-2 | 计算关键指标 | self | in_progress |
| step-3 | 撰写分析报告 | self | pending |

Use plan_update(status, result) to track progress.
```

**实现**（在 `pkg/agent/loop.go` 的 `runLoopFullSystem` 中）：

```go
// After existing system prompt composition, inject [Plan] block if available.
func planFragment(state *LoopState) string {
	if state == nil || state.Plan == nil {
		return ""
	}
	p := state.Plan
	var b strings.Builder
	b.WriteString(fmt.Sprintf("\n\n[Plan]\nTitle: %s\n", p.Title))
	if p.Description != "" {
		b.WriteString(fmt.Sprintf("Description: %s\n\n", p.Description))
	}
	// Table header
	b.WriteString("| Step | Description | Assigned To | Status |\n")
	b.WriteString("|------|-------------|-------------|--------|\n")
	for _, s := range p.Steps {
		b.WriteString(fmt.Sprintf("| %s | %s | %s | %s |\n",
			s.ID, s.Description, s.AssignedTo, s.Status))
	}
	b.WriteString("\nUse plan_update(status, result) to track progress.")
	return b.String()
}
```

## 6. Runner 执行流程

### 6.1 Run 入口

```go
func (r *Runner) Run(ctx context.Context, req *request.RuntimeRequest) <-chan *event.RuntimeEvent {
	ch := make(chan *event.RuntimeEvent, 128)
	go func() {
		defer close(ch)

		// ... 现有 setup 代码 ...

		switch {
		case req.RunMode == request.RunModePlan:
			r.runPlanLoop(ctx, req, ch, runState, policy)
		case len(entryAgent.Handoffs()) > 0:
			r.runTransferLoop(ctx, req, ch, runState, policy)
		default:
			r.runSingleAgent(ctx, req, ch, runState, policy)
		}
	}()
	return ch
}
```

### 6.2 runPlanLoop 核心

```
runPlanLoop(ctx, req, ch, runState, policy):
  │
  ├── planState = plan.NewPlanState()
  ├── accumulated = 0 metrics
  │
  ├── Phase 1: 规划
  │     │
  │     ├── entry = entryAgent.Clone()
  │     ├── entry.ExtraTools += plan_generate (via ToolInfo with interceptor)
  │     ├── entry.SystemInstructions += plan 模式指引
  │     │
  │     ├── [Plan flag = false]
  │     ├── entry.ToolInterceptor = planGenerateInterceptor (if called, set flag)
  │     │
  │     ├── ic = RunLoop(ctx, req, ch, nil, st)
  │     │
  │     ├── if plan flag → PlanState 已填充
  │     │   ├── emit(plan_generated, plan)
  │     │   ├── 返回 tool result to agent conversation
  │     │   └── goto Phase 2
  │     │
  │     └── if no plan → 简单 query
  │         └── goto Done (单 Agent 正常结束)
  │
  ├── Phase 2: Plan 执行
  │     │
  │     ├── st.Plan = planState.Plan()  // Plan 注入 LoopState
  │     ├── current = entryAgent.Clone()
  │     ├── current.ExtraTools += plan_update
  │     ├── current.ToolInterceptor = nil (仅 Phase 1 需要)
  │     │
  │     ├── if current has handoffs → runTransferLoop 内嵌
  │     │     在每个 Agent 运行前刷新 System Prompt [Plan]
  │     │
  │     ├── ic = RunLoop(ctx, req, ch, inheritedMsgs, st)
  │     │   (Agent seen [Plan], uses plan_update as needed)
  │     │
  │     ├── if ic != nil (transfer):
  │     │   ├── 解析目标 Agent
  │     │   ├── emit(agent_transfer)
  │     │   ├── nextAgent.SystemPrompt += [Plan] (刷新)
  │     │   └── goto Phase 2 (下一 hop)
  │     │
  │     └── if ic == nil (Agent 完成)
  │
  ├── Phase 3: 汇总
  │     │
  │     ├── 自动标记所有 pending 为 skipped
  │     ├── emit(plan_step_end, ...)  for remaining
  │     └── emit(query_end, 累计 metrics)
  │
  └── Done
```

### 6.3 关键设计决策

**Q: plan_generate 是否应该被拦截（ToolInterceptor）？**

是。复用与 transfer 相同的 `ToolInterceptor` 机制：
- Agent RunLoop 中调用 `plan_generate` → RunLoop 返回 `*InterceptedCall`
- Runner 在 `runPlanLoop` 中接收 `InterceptedCall`，解析 Plan 存入 PlanState
- 构造工具结果文本返回给 Agent（Plan 创建成功）
- Agent 继续执行下一轮 LLM 调用（此时 System Prompt 已包含 `[Plan]`）

**Q: 如果 Phase 1 Agent 既没有 plan_generate 也没有完成就返回了？**

视为简单 Query。PlanState.Plan 为 nil → 正常结束（如同单 Agent 模式）。

**Q: Phase 2 中 transfer 后 Agent 如何看到 Plan？**

Plan 通过 `LoopState.Plan` 传递。Runner 在 `runTransferLoop` 中每次准备 Agent 前执行 `agent.SystemInstructions += planFragment(st)`。

## 7. 事件

### 7.1 新增事件类型

```go
const (
	EventPlanGenerated EventMessageType = "plan_generated"    // Plan 已生成
	EventPlanStepStart EventMessageType = "plan_step_start"   // 步骤开始执行
	EventPlanStepEnd   EventMessageType = "plan_step_end"     // 步骤完成/失败
)
```

### 7.2 Payload

```go
type PlanGeneratedPayload struct {
	Plan *plan.Plan `json:"plan"`       // 完整 Plan JSON
}

type PlanStepStartPayload struct {
	StepID      string `json:"step_id"`      // 步骤 ID
	Description string `json:"description"`  // 步骤描述
	AssignedTo  string `json:"assigned_to"`  // 执行方
}

type PlanStepEndPayload struct {
	StepID  string            `json:"step_id"`  // 步骤 ID
	Status  plan.PlanStepStatus `json:"status"` // 终态
	Result  string            `json:"result,omitempty"` // 执行结果
}
```

### 7.3 事件发射时机

| 事件 | 时机 |
|------|------|
| `plan_generated` | Phase 1 中 plan_generate 拦截解析成功后 |
| `plan_step_start` | Phase 2 中 Agent 调用 plan_update(status=in_progress) 时 |
| `plan_step_end` | Phase 2 中 Agent 调用 plan_update(status=completed/failed/skipped) 时，或 Phase 3 自动补发 |

### 7.4 事件同步策略

`plan_update` 工具执行后，Runner 需要比较 PlanState 变更并以增量方式发射事件。采用对比法：

```go
// in runPlanLoop, after each tool execution round:
func (r *Runner) emitPlanEventsFromState(
	ch chan<- *event.RuntimeEvent,
	ps *plan.PlanState,
	previous *plan.Plan,
) {
	current := ps.FullSnapshot()
	if previous == nil {
		return
	}
	stepMap := make(map[string]plan.PlanStep)
	for _, s := range current.Steps {
		stepMap[s.ID] = s
	}
	for _, prev := range previous.Steps {
		cur, ok := stepMap[prev.ID]
		if !ok {
			continue
		}
		if cur.Status != prev.Status {
			emit(ch, &event.PlanStepStartPayload{...}) // if cur == in_progress
			emit(ch, &event.PlanStepEndPayload{...})   // if cur is terminal
		}
	}
}
```

### 8.3 Plan 系统 Prompt

```
You are the loopForge test assistant in plan mode.

## Plan Decision Rules

### Call plan_generate when ANY of these is true:
- Task needs 3+ sequential steps where later steps depend on earlier results
- Task needs multi-agent coordination (transfer to different agents)
- Task has independent subtasks that can run in parallel (spawn)
- Steps require different tools or knowledge domains
- Intermediate validation is needed before proceeding
- Number of steps is uncertain — needs iterative execution

### Do NOT call plan_generate when ANY of these is true:
- Single tool call will suffice
- Direct answer without external tools or data
- Conversational follow-up or clarification
- Simple instruction within your own capabilities
- User is correcting or refining within an existing plan

When in doubt, prefer NOT to plan — try direct execution first.
If execution shows the task is more complex, you can plan in the next round.

## Execution Flow
When you DO call plan_generate:
1. FIRST, call plan_generate with a structured plan (title + steps).
2. THEN execute each step, using plan_update to track progress.
3. FINALLY summarize the results for the user.

Use tools (add, subtract, etc.) within each step as needed.
```

## 9. 与现有机制的交互

### 9.1 Plan + Transfer

- Plan 通过 `LoopState.Plan` 在 transfer 中传递
- `runPlanLoop` 检测到 transfer 拦截后，将 `current = next` 继续 Phase 2
- 每个 Agent 的 System Prompt 包含完整 `[Plan]`（包含所有步骤的最新状态）
- 示例：用户 query 需要 A 检索数据 + B 分析数据

```
Phase 1: Agent A（triage）调用 plan_generate → { s1: A检索, s2: B分析 }
Phase 2: Agent A 执行 s1 → plan_update(s1, completed)
         → transfer_to_B → Agent B sees [Plan] with s1 completed
         → Agent B 执行 s2 → plan_update(s2, completed)
Phase 3: 汇总
```

### 9.2 Plan + Spawn

- 父 Agent 生成 Plan 后自主执行步骤
- 如需并行子任务，父 Agent 在步骤中调用 `spawn_subagent`
- 步骤完成后调用 `plan_update`（子 Agent 不感知 Plan）
- 示例：

```
Phase 1: Agent P 调用 plan_generate → { s1: 计算A, s2: 计算B, s3: 汇总 }
Phase 2: Agent P 执行 s1 → spawn_subagent(计算A)
         plan_update(s1, in_progress)
         [spawn child runs]
         plan_update(s1, completed)
         执行 s2 → spawn_subagent(计算B)...
         执行 s3 → 汇总子结果
Phase 3: 完成
```

### 9.3 Plan + Teams（预留）

`PlanStep.AssignedTo` 的 `"team:TeamName"` 值在本版本中被 Runner 接受但不路由。当 Agent 生成 `assigned_to: "team:data-team"` 时，Runner 将其视为 `self`（当前 Agent）并记录日志，提示 team 路由尚未实现。待 v1.0+ agent teams 功能完成后，该值将触发独立 TeamRunner 调度。
